# Chapter 13: OAuth 2.0 & OIDC Security Best Practices

> **Deconstruct delegation protocols, implement state protections to block authentication CSRF, and utilize PKCE on public clients.**

---

## OAuth 2.0 vs. OpenID Connect (OIDC)

*   **OAuth 2.0**: An **authorization** framework that delegates access to resources via Access Tokens (API keys), but does not provide user identity information.
*   **OIDC**: An identity layer built on top of OAuth 2.0 that provides **authentication** by returning an ID Token (JWT format containing user profile details).

---

## Mitigating OAuth CSRF: The `state` Parameter

Authentication CSRF occurs when an attacker forces a victim to link the attacker's social profile (e.g. Google, GitHub) to the victim's local application account.

### The Attack
An attacker starts the OAuth flow, intercepts the redirect code parameter, stops it, and forces the victim's browser to execute the final code exchange request.

### The Defense
Generate a random, cryptographically secure string (the `state` parameter) on the client, store it in the session, and send it to the OAuth provider. The provider returns the same `state` string along with the authorization code. The client validates that the returned state matches the stored state.

```python
# Starting OAuth flow
state = generate_secure_random()
session["oauth_state"] = state
auth_url = f"https://provider.com/auth?state={state}&..."
```

## PKCE (Proof Key for Code Exchange)

For public clients (like Single Page Applications or Mobile Apps) that cannot securely hide client secrets, standard Authorization Code Flow is vulnerable to code interception. **PKCE** mitigates this:

1. **Code Verifier**: A random cryptographic string generated by the client.
2. **Code Challenge**: A SHA-256 hash of the Code Verifier sent with the initial authorization code request.
3. **Verification**: During the code exchange step, the client submits the plain text Code Verifier. The OAuth server hashes it and matches it against the challenge.

---

## Redirect URI Whitelisting

Attackers exploit permissive redirect configurations to leak codes.

```text
Vulnerable config: Redirect URI matching *.example.com or any regex path
Attacker trick: /auth?redirect_uri=https://attacker.com/bypass
```
**Remediation**: Enforce strict, exact matching string lookups for redirect URIs. Never use wildcard domains.

## Interview Points

> **📌 Interview Point 1: What is the purpose of PKCE?**
> PKCE (Proof Key for Code Exchange) prevents authorization code interception attacks. Since public clients cannot protect a client secret, PKCE uses a one-time dynamic challenge/verifier combination to verify that the client requesting tokens is the exact client that initiated the auth flow.
