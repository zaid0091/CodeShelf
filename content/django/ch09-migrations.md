# Chapter 9: Migrations

## 9.1 What are migrations?

> **Definition:** **Migrations** are version-controlled Python files describing schema changes to your database. Django generates and applies them from [model](./ch03-models-orm.md) changes.

```text
blog/migrations/
├── __init__.py
├── 0001_initial.py
└── 0002_post_slug.py
```

## 9.2 Basic workflow

```bash
# After changing models.py
python manage.py makemigrations
python manage.py migrate

# Check status
python manage.py showmigrations
```

| Command | Action |
|---------|--------|
| `makemigrations` | Create migration files from model diffs |
| `migrate` | Apply pending migrations to DB |
| `showmigrations` | List applied `[X]` vs pending `[ ]` |
| `sqlmigrate app 0001` | Show SQL for a migration |

## 9.3 Example migration file

```python
# Generated by Django — simplified
from django.db import migrations, models

class Migration(migrations.Migration):
    dependencies = [
        ("blog", "0001_initial"),
    ]

    operations = [
        migrations.AddField(
            model_name="post",
            name="slug",
            field=models.SlugField(default="", max_length=200),
            preserve_default=False,
        ),
    ]
```

## 9.4 Common operations

| Operation | Use |
|-----------|-----|
| `CreateModel` | New model |
| `DeleteModel` | Remove model |
| `AddField` / `RemoveField` | Column changes |
| `AlterField` | Change field type/options |
| `RenameModel` / `RenameField` | Renames |
| `RunPython` | Data migration |

## 9.5 Handling nullable fields

When adding a required field to existing rows:

```python
# Step 1: Add with null=True or default
slug = models.SlugField(null=True)

# Step 2: Populate data (RunPython or shell)
# Step 3: Remove null=True, makemigrations again
slug = models.SlugField(unique=True)
```

Or provide a one-off `default=` in the migration.

## 9.6 Data migrations

```python
from django.db import migrations

def forwards(apps, schema_editor):
    Post = apps.get_model("blog", "Post")
    for post in Post.objects.all():
        post.slug = slugify(post.title)
        post.save(update_fields=["slug"])

class Migration(migrations.Migration):
    dependencies = [("blog", "0002_post_slug")]
    operations = [
        migrations.RunPython(forwards, migrations.RunPython.noop),
    ]
```

Use `apps.get_model()` — not direct model imports — in migrations.

## 9.7 Squashing migrations

```bash
python manage.py squashmigrations blog 0001 0005
```

Combines many migrations into one for cleaner history on long-running projects.

## 9.8 Fake migrations

```bash
python manage.py migrate blog 0003 --fake
```

Marks migration as applied without running SQL — use carefully when DB already matches.

## 9.9 Rollback

```bash
python manage.py migrate blog 0001
```

Migrates **to** a named migration, reversing later ones.

## 9.10 Best practices

| Practice | Reason |
|----------|--------|
| Commit migrations to git | Team shares same schema |
| One logical change per migration | Easier rollback |
| Test migrations on copy of prod data | Catch lock/timeout issues |
| Never edit applied migrations | Create new migration instead |

## 9.11 Zero-downtime considerations

- Add nullable columns first, backfill, then enforce constraints
- Use `SeparateDatabaseAndState` for complex refactors
- Plan index creation on large tables during low traffic

## Exercises

1. Add a `slug` field to Post; run makemigrations and migrate.
2. Run `showmigrations` and `sqlmigrate` for your latest migration.
3. Write a data migration to populate slugs from titles.
4. Practice rollback: migrate to previous migration, then forward again.

## Summary

Migrations keep database schema in sync with models. Run `makemigrations` after model changes and `migrate` to apply; use data migrations for row-level transforms.
